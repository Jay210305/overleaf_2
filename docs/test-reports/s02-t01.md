# S02-T01 — Trusted registration and email verification

**Status:** Implementation tested locally; independent co-maintainer review pending. **Branch:** `feature/identity-permissions` tracking `origin/feature/identity-permissions`. **Base:** `b75ef65` (includes merged S01 prerequisite). **Environment:** Windows, Node 24, pnpm 11.25.0 from the installed local CLI, PostgreSQL 17 and Mailpit via Compose. **Actual effort:** not measured.

## Scope and behavior

- Added operator-issued, email-bound trusted invitation tokens. The operator command emails the secret and never prints it; unknown-user public signup remains disabled. This is the G1 route to registration until G5 approval.
- `POST /api/v1/auth/register` validates the shared DTO, exact Origin, custom CSRF header and invitation. It persists a normalized unique email and Argon2id password hash, consumes the invitation under row locks and creates a hashed 24-hour verification token. SMTP failure invalidates the undelivered token and restores the invitation for retry.
- `POST /api/v1/auth/verify-email` consumes the token once under row locks; expired, reused and disabled-account requests are denied. API errors use `application/problem+json`; request logging does not include credentials or token-bearing headers.
- The shared transaction client now preserves deliberate application errors raised inside a transaction instead of mapping every string `code` to a database failure.
- No schema migration was needed: the existing `users` and `verification_tokens` tables were used. `SMTP_URL` and `EMAIL_FROM` are optional server configuration; without a mail sender the registration route returns 503.
