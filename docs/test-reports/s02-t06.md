# S02-T06 — Authentication rate limits and log redaction

**Status:** Done; independent co-maintainer accepted on 2026-10-11. **Branch:** `feature/identity-permissions` tracking `origin/feature/identity-permissions`. **Base:** accepted S02-T05 closure commit `0eed01b` (sprint base `b75ef65`). **Environment:** Windows, Node 24, pnpm 11.25.0, local PostgreSQL 17, Redis 7 and Mailpit, Edge browser. **Actual effort:** not measured.

## Scope and behavior

- The production API requires Redis at startup and constructs a limiter. Its atomic fixed-window counter is keyed by the client socket IP digest and auth route digest, shared across instances. Register and forgot allow 5 requests per minute; verify, login and reset allow 10; session read and logout allow 60. A denied request returns 429 `application/problem+json`, `RATE_LIMITED` and positive integer `Retry-After` seconds, exposed to the browser through CORS. Redis failure after startup returns 503 for auth routes; it does not allow an uncounted request.
- Fastify's logger serializes requests to method only, replies to status only and errors to fixed redacted fields. Bodies, queries and headers supplied to structured log calls are redacted. Error responses remain generic and use generated request IDs. The existing Origin, CSRF, account and token checks still run for admitted requests.
- Browser auth forms from S02-T05 already display 429 and network states. This slice adds a real server 429; the browser test's intercepted 429 remains UI coverage, not proof of server limiting.
