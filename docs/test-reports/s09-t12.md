# S09-T12 — Implement explicit ownership transfer

**Status:** IN_PROGRESS (task implementation complete; pending sprint completion). **Branch:** `codex/sprint-09-history-review` tracking `origin/codex/sprint-09-history-review`. **Base:** `main`. **Environment:** Linux (x86_64), Node 24+, pnpm 11.25.0, local Docker Compose PostgreSQL 17, Redis 7. **Actual effort:** 8 h.

## Scope and acceptance evidence

- Implemented explicit, atomic ownership transfer workflow in `apps/api/src/modules/projects/ownership.ts`:
  - `POST /api/v1/projects/:projectId/ownership`: project owner creates an expiring ownership transfer offer for a designated recipient; validates recipient existence, prevents self-transfer, and cancels any previously pending offers.
  - `POST /api/v1/ownership/:offerId/accept`: recipient accepts the offer in an atomic transaction that reassigns project ownership (`owner_id`), removes recipient from project members, demotes former owner to `EDITOR`, and marks offer as accepted. Validates recipient identity, expiration, and pending status.
  - `DELETE /api/v1/projects/:projectId/ownership/:offerId`: project owner cancels/revokes a pending transfer offer.
- Added database table `project_ownership_offers` in `packages/db/migrations/0002-support.sql` with indices on `project_id` and `recipient_user_id`.
- Enforced server-side authorization: offer creation and cancellation require project action `TRANSFER` (granted strictly to `OWNER`), rejecting non-owners with 403.
- Added comprehensive test suites:
  - `tests/integration/s09-t12.test.ts`: exercises offer creation, bystander rejection (403), recipient acceptance, former owner demotion to editor, duplicate accept conflict (409), self-transfer rejection (400), and cancellation.
  - `tests/regression/pro-13/s09-t12.test.ts`: verifies PRO-13 requirement that ownership remains intact until explicit recipient acceptance.
  - `tests/regression/col-03/s09-t12.test.ts`: verifies COL-03 requirement that non-owners are denied offer creation with 403.
