# S12-T03 — Pull using checkpoint and base SHA

**Status:** DONE — implemented and green on all gates; accepted by the user as independent co-maintainer review on 2026-10-16. **Branch:** `codex/sprint-12-github-sync` tracking `origin/codex/sprint-12-github-sync`. **Base:** `0555e8d` plus S12-T01 (`31468e5`) and uncommitted S12-T02 work. **Environment:** Windows, Node 24, pnpm 11.25.0, local PostgreSQL/Redis/MinIO (Docker Desktop). **Actual effort:** Not measured.

## Scope and acceptance evidence

- `apps/jobs/src/sync/github-pull.ts` builds a pull plan for a linked GitHub repo/branch: the caller's `expectedRemoteSha` must match both the stored `sync_cursor` and the freshly read remote head, otherwise 409 REMOTE_CONFLICT with nothing recorded — a divergent remote SHA never becomes fake synced.
- Remote paths are validated before any local snapshot: traversal (`..`), absolute paths, backslashes, NUL, `.`/empty segments → 400 VALIDATION_ERROR; per-file > 25 MiB, total > 100 MiB or > 2,000 files → 413 QUOTA_EXCEEDED. `.git`, dotenv secrets and TeX build output (`.aux/.log/.out/.toc/.synctex.gz/.fls/.fdb_latexmk/.pem/.key`) are ignored by policy.
- The local canonical state is snapshotted as an immutable checkpoint revision (`source: github-pull`, `Pre-pull snapshot`) before classification; text fingerprints replay `crdt_updates` (`sha256("text:" + canonical text)`), binary fingerprints hash the content-addressed `blob_key`. A caller-provided `sourceRevisionId` is reused without a new snapshot; unknown/foreign revision IDs → 404.
- Three-way classification against the recorded agreement (`project_integrations.sync_base_manifest`): `unchanged` / `update` / `keep-local` / `delete` / `keep-deleted` / `add` / `conflict`, sorted by path. Without an agreement the classification is conservative: shared paths are conflicts, never overwrites. Conflicts are surfaced as `text`, `binary` or `tree` (delete-vs-edit and file/folder kind mismatch); binary conflicts always require an explicit choice.
- Nothing is applied to live Yjs state: the service reads `crdt_updates` only for fingerprints and never writes project content; applying remote changes through the canonical service is S12-T08 work. Automatic force push or direct snapshot DB replacement bypassing live Yjs is not implemented anywhere in the slice.
- Failure mapping: token expiry → 401 TOKEN_EXPIRED; provider failure → 502 PROVIDER_UNAVAILABLE (no provider detail leaked); inactive/missing connection → 401 CREDENTIALS_MISSING; viewer/stranger → 404 RESOURCE_NOT_FOUND (owner and active OWNER/EDITOR members allowed). The provider token never appears in the result or logs.
- New migration `packages/db/migrations/0013-github-sync-base.sql` adds a nullable `sync_base_manifest` jsonb to `project_integrations`. A fully clean pull records the agreement (local fingerprints + remote SHAs), advances `sync_cursor` and sets `last_synced_revision`, so later pulls classify precisely instead of conservatively; malformed agreements degrade to conservative mode.
- Tests: `tests/integration/s12-t03.test.ts` (10), `tests/regression/int-05/s12-t03.test.ts` (7), `tests/regression/col-12/s12-t03.test.ts` (7).

## Remaining work and limits

- Remote reads go through an injected fixture reader; real GitHub I/O stays BLOCKED_BY_CREDENTIALS (GAP-04). Applying pulled content through the live canonical service is S12-T08; the push guard is S12-T04.
- Remote file bytes are not fetched during planning: conflict kinds use the frozen local kind; S12-T08 fetches remote bytes at apply time and can re-classify a text-marked file that turns out binary.
- The agreement writer records only on fully clean pulls; base updates after partial conflict resolutions belong to S12-T08.
- INT-05 and COL-12 remain IN_PROGRESS until all mapped S12 tasks complete.
