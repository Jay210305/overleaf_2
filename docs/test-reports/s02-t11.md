## Scope and behavior

- `POST /api/v1/me/avatar` accepts only a PNG at most 1,000,000 bytes and 1024 pixels on each side. The API checks PNG chunk CRC, dimensions, compression and row filters; requires the current verified, enabled account's opaque session, exact Origin and session CSRF; and ignores no caller-selected user or object key. It stores the bytes in a private `avatars/<user-id>/<uuid>.png` object, then updates the current user's `avatar_key` under session/user locks.
- The profile returns an account-scoped `avatarUrl`. `GET /api/v1/me/avatar/content` obtains the object key only from the authenticated user's database row. No public URL or direct object key is returned. The browser fetches the image with credentials and shows a local blob preview; it uploads raw PNG bytes with the current CSRF token.
- Replacement adds the old object to `avatar_cleanup_jobs` in the same database transaction as the new reference. A bounded worker rechecks that no live profile references the old key, deletes the private object and marks the job processed. Failures retry later. A failed metadata transaction attempts to remove the newly uploaded object.
- Migration `0004-avatar-cleanup.sql` is required before deployment of this API version. Static OpenAPI copies include the binary upload and private content route with `IN_PROGRESS` markers. OpenAPI generation/DTO parity remains GAP-12.
