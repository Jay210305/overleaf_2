# S05-T10 — Apply validated ZIP as a consistent project

**Status:** Implementation verified locally on 2026-10-13; independent co-maintainer review pending. **Branch:** `codex/sprint-05-assets-import-export` (base `origin/main` at `40f0870` plus Sprint 04 merge `d09db72`). **Environment:** Windows, Node 24.20.0, pnpm 11.25.0, local Docker Compose PostgreSQL and MinIO. **Actual effort:** Not measured.

## Scoped behavior

- `readArchiveForApply` repeats the bounded ZIP scan and compares the complete validated manifest to the actual bytes. Apply also checks the server-owned archive key, object size and SHA-256 before any project row is written. It checks the persisted manifest and fingerprint again after project-ID reservation and under the transaction's job-row lock, rejecting a version mismatch or changed manifest before commit.
- Migration `0008-import-project-reservation.sql` reserves one unique pending project ID. Binary files are copied and read back under deterministic private `projects/<projectId>/blobs/<sha256>` keys. A failed object write or database transaction leaves the job validated and retryable with the same ID.
- `applyValidatedImport` locks the job row and commits the owner project, explicit and implicit folders, files, one canonical Yjs update per text file, selected main `.tex` file and `succeeded` job transition in one PostgreSQL transaction. Concurrent and repeated calls return the same project ID. The public job status does not expose the pending ID or object keys.
- The private `imports:apply --once` command processes a bounded validated-job pass. Invalid archives move to failed; outages remain retryable with a durable one-minute delay so an old outage does not starve later jobs. Failed jobs with a reserved but uncommitted project are cleaned in bounded passes, including their unreferenced prepared blobs. A successful source archive is swept after 14 days; current project blobs are retained.
