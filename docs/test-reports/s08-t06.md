# S08-T06 — Mention and in-app notifications

**Status:** IN_PROGRESS; implementation complete with focused PASS evidence, independent review pending. **Branch:** `codex/sprint-08-sharing-comments-chat` tracking `origin/codex/sprint-08-sharing-comments-chat`. **Base:** `a568117` (`origin/main`, after S07). **Environment:** Windows, Node 24.20.0, pnpm 11.25.0, local PostgreSQL fixture. **Actual effort:** Not measured.

## Implemented and observed

- Comment and reply creation call `createMentionNotifications` inside the same PostgreSQL transaction (`apps/api/src/modules/comments/routes.ts`). Only current project members with verified, enabled accounts and opt-in `user_preferences.notification_settings_json` receive a row; the actor is excluded and foreign-user mentions are rejected with 400 before any write.
- `packages/db/migrations/0012-notification-idempotency.sql` adds a unique index on `(user_id, type, payload_json->>'sourceId')` for `mention`/`reply` types; the insert uses `ON CONFLICT DO NOTHING`, so repeated publication of the same source stores exactly one row. Reply creation additionally notifies the parent comment author with type `reply`.
- `GET /api/v1/me/notifications` returns newest-first `{items,nextCursor}` with a project-scoped UUID cursor and shows only rows whose project is active and still grants the reader membership; revoked members see an empty feed. `PATCH /api/v1/me/notifications/{id}/read` requires exact Origin, session and CSRF, sets `read_at` once (repeat reads return the same timestamp), and returns 404 for foreign or post-revocation rows with 403 on forged CSRF. Payloads carry IDs and project title only, never comment bodies.
- `apps/web/src/features/notifications/list.tsx` renders the notification region on the dashboard with mark-read persistence and older-page retention; bodies render through React text nodes.
- Contract slice documented in `docs/contracts/http-api.md` (G2 Mention and In-App Notification Slice).
