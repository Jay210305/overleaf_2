# S09-T03 — Restore file or project with version guard

**Status:** IN_PROGRESS (task implementation complete; pending sprint completion). **Branch:** `codex/sprint-09-history-review` tracking `origin/codex/sprint-09-history-review`. **Base:** `main`. **Environment:** Linux (x86_64), Node 24+, pnpm 11.25.0, local Docker Compose PostgreSQL 17, Redis 7. **Actual effort:** 8 h.

## Scope and acceptance evidence

- Implemented `RestoreService` and `registerRestoreRoutes` in `apps/api/src/modules/history/restore.ts`.
- Enforced `expectedRevision` optimistic concurrency guard: stale `expectedRevision` returns `409 REVISION_CONFLICT` without modifying project state.
- Supported single-file restore via `fileId` (restoring only the requested node while preserving all other files) and whole-project restore.
- Restores content by creating a new immutable revision (`source: "restore"`) rather than rewriting or erasing prior history.
- Enforced server-side authorization: Action `RESTORE` is granted to OWNER and EDITOR; REVIEWER and VIEWER are rejected with 403; foreign actors with 404.
- Invariant verified: Project ownership, memberships, roles, and ACLs remain completely intact across restorations.
- Added test suites:
  - `tests/integration/s09-t03.test.ts`: exercises expectedRevision conflict detection (409), single file restore, full project restore, permission matrix, and ACL preservation.
  - `tests/regression/col-11/s09-t03.test.ts`: verifies COL-11 requirement that file or project restore creates a new revision without altering collaborator roles.
  - `tests/regression/nfr-06/s09-t03.test.ts`: verifies NFR-06 requirement that restored revision generates exact deterministic manifest and hash.
