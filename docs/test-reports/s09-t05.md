# S09-T05 — Resolve proposals with explicit conflicts

**Status:** IN_PROGRESS (task implementation complete; pending sprint completion). **Branch:** `codex/sprint-09-history-review` tracking `origin/codex/sprint-09-history-review`. **Base:** `main`. **Environment:** Linux (x86_64), Node 24+, pnpm 11.25.0, local Docker Compose PostgreSQL 17, Redis 7. **Actual effort:** 8 h.

## Scope and acceptance evidence

- Implemented proposal resolution service and REST routes in `apps/api/src/modules/review/resolve.ts`:
  - `POST /api/v1/projects/:projectId/suggestions/:suggestionId/resolve`: resolves a single proposal (`accept` or `reject`). On accept, applies changes to target node and updates status to `accepted`; on reject, sets status to `rejected` without modifying source text. If context hash mismatches (`expectedOldTextHash`), updates status to `conflict` and returns 409 `SUGGESTION_CONFLICT`.
  - `POST /api/v1/projects/:projectId/suggestions/bulk-resolve`: executes atomic resolution per item across an array of up to 100 proposals. Returns per-item results (`accepted`, `rejected`, or `conflict`) and guarantees unapplied conflicting suggestions are never falsely marked as accepted.
- Enforced server-side authorization: routes are guarded by project action `REVIEW`, permitted to OWNER and EDITOR; REVIEWER and VIEWER requests are rejected with 403.
- Implemented UI component `SuggestionCard` in `apps/web/src/features/review/suggestion-card.tsx` providing accessible accept/reject controls, conflict warnings, and status badges.
- Added comprehensive test suites:
  - `tests/integration/s09-t05.test.ts`: exercises single accept, repeat accept (409), reject (unchanged text), context hash conflict (409 and conflict status), role denials (403 for REVIEWER/VIEWER), and bulk resolution.
  - `tests/regression/col-09/s09-t05.test.ts`: verifies COL-09 requirement that bulk resolution never marks an unapplied suggestion as accepted when a conflict occurs.
