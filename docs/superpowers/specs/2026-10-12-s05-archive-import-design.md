# S05 Archive Import Design

**Status:** Design approved in conversation on 2026-10-12; written-spec review pending. **Branch:** `codex/sprint-05-assets-import-export`. **Scope:** S05-T03 archive validation and durable staged job, new S05-T12 authenticated ZIP intake, and the interface consumed by S05-T10 project application. S05-T03 product work remains behind independent S05-T02 acceptance.

## Intent and current boundary

A signed ZIP upload should eventually create a new project with nested source and assets, without path traversal, symlinks, decompression bombs, duplicate nodes or partial state. The project must not appear until S05-T10 applies a completely validated archive. Retries must refer to one durable job. The current S05-T01 upload route creates project file nodes and rejects `.zip`; the planned `POST /api/v1/projects/imports` accepts an upload ID but has no live implementation. An archive therefore needs a separate intake flow.

## Approaches considered

1. **Separate signed intake, private validator and project apply (chosen).** S05-T12 binds a short-lived signed ZIP PUT to an authenticated actor and creates a durable job; S05-T03 validates privately; S05-T10 applies the validated result. The stages have independent tests and prevent an archive from becoming a project file.
2. **Reuse S05-T01 project uploads.** This would let ZIP bytes enter an existing project, but its completion creates a normal node and its allowlist rejects ZIP. Changing that route would mix import staging with project-file semantics.
3. **Proxy and extract ZIPs in the API request.** This could reduce endpoints, but would hold a long-running decompression in the API and make crash recovery and per-job status harder.

S05-T12 is a new task ID, not a rename of S05-T03. Its task record, dependency edges, roadmap/index rows and traceability are created during planning after this written spec is approved. S05-T03 remains the validator and job-state owner; S05-T10 remains the sole project-state writer.

## Components and data flow

S05-T12 adds a session-guarded presign route for ZIP input and completes the planned `POST /projects/imports` contract with `{uploadId, title}` plus `Idempotency-Key`. Presign records actor ID, expected size and SHA-256, server-created key, and a five-minute expiry. It signs PUT only for `imports/<actorId>/uploads/<uploadId>`. Completion repeats current account, Origin and CSRF checks; it reads at most 25 MiB from private storage and recomputes the hash and size. It reserves one durable job in `staging` state, copies the verified bytes to its server-only `imports/<actorId>/jobs/<jobId>/source.zip` key that is never presigned, verifies that copy, and moves the job to `queued`. The API returns `202` with a job ID only after this transition; no project is created yet. A job status read is actor-scoped and never returns object keys or signed URLs.

S05-T03 owns an `import_jobs` PostgreSQL migration, a narrow typed reserve/claim repository callable by the API and worker, and `apps/jobs/src/imports/zip.ts`. The repository stores actor ID, hashed idempotency key, request fingerprint (archive SHA-256, size and title), private archive key, status, lease/attempt metadata, versioned validated manifest, error code and eventual project ID. A unique actor/key constraint serializes concurrent submissions. The same key and fingerprint returns the same job, including a failed job; the same key with changed input returns 409. A different key is needed to intentionally retry a rejected archive. A `staging` row reserves its deterministic server-only object key before the copy. If copying or the final status update fails, a retry with the same key can inspect the recorded key and hash and safely complete staging; no untracked object is created. The worker claims queued or expired-lease validation rows, reads only the database-bound archive key, verifies its SHA-256 again, and transitions `queued → validating → validated` or `failed`. An expired lease permits crash recovery. It writes no project, node or canonical text rows.

S05-T10 consumes only `validated` jobs. It re-reads the server-owned archive, verifies the immutable archive digest and each manifest entry hash, then applies the ID-based tree, binary blobs and canonical Yjs text in its own consistent mutation boundary. Only that later step may set a project ID and mark an import `succeeded`. A validated job must not be reported as a completed project. The planned generic `JobView` cannot express this distinction, so the import-specific status DTO and OpenAPI operation will be adjusted during S05-T12 without changing unrelated jobs.

The object adapter will allow an explicit `imports/` prefix and enforce actor/job scope at callers. It must not accept a client-supplied key. Expired signed-upload objects are cleaned only after URL expiry; S05-T12 owns that cleanup. A queued or validated job archive remains retained until application. S05-T03 deletes the server-only archive for a permanently rejected job, retrying failed deletes from the still-durable job row. S05-T10 schedules deletion of succeeded-job archives after the documented 14-day transient retention; its own project source remains durable. No archive is extracted to a filesystem path.

## ZIP validation

Use a reviewed, exact-pinned central-directory parser; `yauzl` 3.4.0 is the current candidate (MIT, with lazy entry iteration, strict filename handling and entry-size checks documented in its [README](https://github.com/thejoshwolfe/yauzl/blob/master/README.md) and [package metadata](https://github.com/thejoshwolfe/yauzl/blob/master/package.json)). Dependency installation and lockfile change wait for the implementation plan. The worker iterates one entry at a time and streams decompressed bytes with its own counters; metadata checks alone are insufficient.

The starting limits from the storage contract are 25 MiB compressed ZIP, 100 MiB total expanded content, 2,000 file/folder nodes including implied directories, 25 MiB per file and maximum 100:1 expansion per compressed entry. Abort as soon as any actual-byte cap is crossed. Reject absolute or drive paths, backslashes, empty/dot/dot-dot segments, control characters, percent-encoded traversal, non-NFC names, duplicate normalized paths, symlinks and other non-regular entry types, encrypted entries, unsupported compression methods and nested archives. Validate allowed source/asset extensions and decoded UTF-8 or binary magic using the same server policy as regular uploads; extract that policy into a server-only shared module before depending on it from both paths. Directory entries create tree structure only; files are SHA-256 hashed and CRC-32 checked against the central directory from actual decompressed bytes. The sorted versioned manifest stores normalized paths, content kind, MIME, size and SHA-256, but no source bytes. The archive key and source content are never logged.

Unsafe paths are classified as 400, byte/node limits as 413, and symlink, malformed/archive-content or hash failures as 422. The asynchronous worker persists the corresponding redacted `error_code` and marks the job failed; no project or partial node is visible. Service outages remain retryable and are distinct from permanently invalid ZIPs. S05-T12 uses `application/problem+json` for errors detectable during intake, while its later status read exposes only the safe validation code and state.

## Verification and handoff

S05-T03 starts with failing positive and hostile ZIP fixtures: nested TeX/assets; traversal and encoded traversal; absolute/drive/backslash paths; duplicate normalized names; symlink/special/encrypted entries; forged size and CRC; high-ratio and over-limit expansion; nested ZIP; unsupported MIME and invalid text. Verify actual stream counters, manifest hashes, no project mutation, concurrent idempotency and lease recovery. Run real PostgreSQL and MinIO integration tests for job persistence and private archive reads, plus the task's lint, typecheck, build, planning and security gates. Record commands and unmet checks in `docs/test-reports/s05-t03.md`; no mocked provider or written plan counts as runtime evidence.

S05-T12 later proves denied/foreign/disabled sessions, exact Origin and CSRF, scoped signed PUT, hash/size mismatch, duplicate-key behavior, and expired intake cleanup with real services. S05-T10 proves atomic project creation, canonical Yjs text and retry without duplicate projects. S05-T08 remains the final hostile ZIP and import/export journey. Independent co-maintainer review and the dependency order in `AGENTS.md` govern `done` status for every task.
